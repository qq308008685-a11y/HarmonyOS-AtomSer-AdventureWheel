## 生成与复核

发布流程采用 [harmony-case-publisher](https://gitcode.com/HmosDevBPC/case-skill/tree/main/skills/general/harmony-case-publisher)，发布包字段和格式以其采用的 [harmony-case-generator](https://gitcode.com/HmosDevBPC/case-skill/tree/main/skills/general/harmony-case-generator) 为准。当前核对的上游提交为 `372374590fe110d75adf4427920c015b716a45ae`。再次更新规则时先读取所用版本的 Skill、字段规范和 README 映射要求，不沿用历史记录中的旧要求。

README 保持普通案例的八章结构；教程固定为五个 H2，依次为“快速体验、完整实践、功能检查与排障、安全与清理、进阶实践”，不复制整篇 README。普通案例通用检查兼容第三段标题“高频问题排查”，本案例使用“功能检查与排障”。介绍概述、适合人群和架构说明使用 HTML 富文本；场景扩展和拓展实践仍为选填，前置条件数量及知识点副标题不套用无依据的固定条数。封面、卡片、分享、架构及手机预览继续使用现有正式图片。

1. 按所用 Skill 的入口，用原版 `scripts/validate_case.py` 检查 `cases/`，要求 V-1 至 V-13 通过且图片检查未跳过。
2. 在工程根目录运行：

```powershell
node .\tools\check-case-package.mjs
```

该工具检查当前案例字段、富文本结构、本地媒体尺寸与引用、编辑器黑名单、仓内文档链接、五段 H2 顺序及 README 教学范围映射，无需依赖维护者电脑上的 Skill 绝对路径。提示词按对应区段核对数量、顺序与内容；进阶只映射 README“深入阅读与扩展”子章节，排除“关键目录”的目录树。注释与代码块中的伪标题不参与 H2 计数；少块、换序、跨段移动及额外 H2 都不能通过。它不替代原版校验、内容事实审阅、图片视觉检查或平台验收。单图 500 KiB 是加载建议，硬性单文件上限为 20 MiB。

3. 按实际变更范围运行业务规则与备份拆分测试，分别记录结果；需要构建或设备操作时留下当前证据，不复用旧日期作为新运行。
4. 核对教程与 README 提示词逐段一致、图片文字与实际代码和数据一致；在桌面与手机宽度检查排版、图片、表格和链接。
5. 只有获得 Git 写入授权后，才精确暂存公开文件，并运行 `node .\tools\check-public-source.mjs` 和 `git diff --cached --check`。扫描对象是真实 Git 索引，不是未暂存的工作目录；不能把内部检测材料、私钥、口令或个人数据带入提交。

本地文件通过不等于云端体验、空项目全程复现或平台导入通过。

## 导入与发布验收

1. 经维护者确认后，将当前源码与 `cases/` 提交、推送到上述仓库。
2. 无登录凭据读取默认分支的 JSON、教程和全部引用媒体，比较实际字节；不能只凭网页返回 HTTP 200 判断原文件可读。
3. 在平台执行“从公仓导入”，读取仓库的 `cases/`；当前不以独立 ZIP 作为交付环节。
4. 核对标题、学习时长、卡片、封面、知识点、五段教程、八步完整实践、全部提示词、批量迁移入口、架构和手机预览。检查富文本处理后的样式、图片、表格、来源链接和锚点，不把本地浏览器结果当作平台验收。
5. 有真实平台结果后记录操作日期、来源提交及问题，未验证项继续保留。
